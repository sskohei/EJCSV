# テスト方針

ポートフォリオ規模のプロジェクトとして、費用対効果の高い範囲に絞ってテストを整備する。

## バックエンド（pytest）— 優先度高

### ユニットテスト

- `parsing.py`: 改行/カンマ分割、trim、重複保持（行を消さない）、小文字化・空白正規化のルール。
- `dictionary_service.py`: 大文字小文字を無視した一致、フレーズ（複数語見出し語）の検索、未ヒット時に `None` を返すこと。
- `sentence_service.py` / ビルド時の例文選定ロジック: 単語境界での一致（部分文字列にマッチしないこと）、4〜25語フィルタ、同点時の `sentence_id` 最小によるタイブレークの決定性、候補ゼロ時の空欄化。
- `csv_service.py`: ヘッダを含めないこと、UTF-8 BOMの付与、カンマ/引用符を含む値の自動クオート、空欄セルの扱い。

### 統合テスト

- FastAPIの `TestClient` を使い、`/api/lookup` と `/api/export/csv` の両ルーターをテストする。
- DB依存は**本番の `ejcsv.db` に依存せず**、`tests/fixtures/build_test_db.py` で構築した少数の既知単語・例文からなる小さなfixture SQLite DBに差し替える（FastAPIの依存性注入をテスト用にオーバーライドする）。これによりテストの高速化と決定性を確保する。
- カバーするケース: 通常のリクエスト、単語数超過（422）、未知の単語（該当セルは空欄だが行は残る）、CSVダウンロードのヘッダ・Content-Type・本文内容。

## フロントエンド

- MVPでは重いE2E（Playwright等)は導入しない。
- 入力パース・バリデーション表示・結果テーブルのレンダリングなど、ロジックが単体で切り出せる部分についてはVitest + React Testing Libraryで最小限のテストを書く。
- Playwrightによる「単語入力→プレビュー→CSVダウンロード」までのE2Eテストは、**意図的に後回しにするV2/ストレッチ項目**として明記する（忘れているのではなく、優先度判断として見送っている旨を残す）。

## 認証・検索履歴のテスト

- Supabase AuthのGoogleログイン成功・ログアウト・認証切れを確認する。
- 未ログインでも検索プレビューとCSV出力が利用できることを確認する。
- ログイン中の検索成功時だけ履歴が保存されることを確認する。
- 履歴一覧・詳細・削除が本人の履歴だけを対象にすることを確認する。
- RLSにより、別ユーザーの履歴を取得・削除できないことを確認する。
- 履歴保存が失敗しても、検索結果表示とCSV出力が失敗しないことを確認する。

### 自動テストの対応範囲

フロントエンドのVitestでは、Supabase SDKとNext.js APIルートをモックし、外部サービスの認証情報に依存せず次の挙動を検証する。

| 対象                | 確認内容                                                                       |
| ------------------- | ------------------------------------------------------------------------------ |
| `AuthButton`        | Googleログイン開始、ログアウト、セッション取得失敗、未設定時の無効化           |
| `/auth/callback`    | OAuthコード交換後のリダイレクト、外部URLへのオープンリダイレクト防止、交換失敗 |
| `/api/lookup`       | 認証済み検索の保存、未認証時の未保存、履歴保存失敗時の検索継続                 |
| `/api/history`      | 未認証401、本人の一覧取得、新しい順の指定                                      |
| `/api/history/{id}` | 本人の詳細取得・削除、他ユーザー／不存在IDの404、未認証401                     |
| `/history`          | 一覧、詳細再表示、削除、空状態、認証切れ、取得失敗                             |

```bash
cd frontend
npm test
npm run lint
npx tsc --noEmit
```

### RLSの手動確認

RLSはSupabaseプロジェクトの認証セッションを使うため、リリース前に実環境またはローカルSupabaseで次を確認する。ユーザーA・Bは別Googleアカウントを使う。

1. Aでログインして検索し、履歴一覧にAの履歴が表示されることを確認する。
2. Bでログインして、Bの履歴一覧にAの履歴が表示されないことを確認する。
3. Aの履歴IDを指定した詳細取得・削除リクエストをBのセッションから実行し、404または対象なしとなり、Aの履歴が変更されないことを確認する。
4. Aでログアウト後に履歴一覧・詳細・削除を実行し、401になることを確認する。
5. Supabase SQL Editorで次を実行し、RLSと3ポリシーが存在することを確認する。

```sql
select relrowsecurity
from pg_class
where oid = 'public.search_histories'::regclass;

select policyname, cmd
from pg_policies
where schemaname = 'public'
  and tablename = 'search_histories'
order by policyname;
```

`relrowsecurity`は`true`で、`SELECT`・`INSERT`・`DELETE`のポリシーが1件ずつ返ることを期待する。Service Role Keyを使った確認はRLSを迂回するため、ユーザー分離の検証には使用しない。

## CI（任意・nice-to-have）

`.github/workflows/ci.yml` でプッシュ時に以下を実行することを検討する（ポートフォリオとしての完成度を示すシグナルとして有用だが、MVPの必須要件ではない）:

- バックエンド: `pytest`
- フロントエンド: lint（eslint）・型チェック（tsc）・build

具体的なワークフロー定義は実装時に整備する。
