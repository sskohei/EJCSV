# データパイプライン

EJDictとTatoebaの生データから、バックエンドが実行時に高速に参照できるSQLiteデータベース（`ejcsv.db`）をオフラインでビルドする手順・設計をまとめる。**このビルドはリクエスト時には一切行わない。** 事前に1回（またはデータ更新時のみ）実行し、結果のDBファイルを配布する。

## なぜ事前ビルド方式か

- Tatoebaの英語データは約203万文（展開後104MB）あり、これをリクエストごとに走査したりメモリに全展開したりするのは小規模なポートフォリオ用バックエンドには不向き。
- 単語→訳語、単語→例文という「最終的な答え」を事前に計算し、SQLiteの主キー検索（O(1)相当のインデックス点検索）として引けるようにしておけば、実行時のメモリ・CPU消費は最小限で済み、起動も高速。

## ビルドスクリプト: `backend/scripts/build_data.py`

### 1. EJDictの読み込み・正規化

- 入力: `backend/data/raw/ejdict/src/a.txt` 〜 `z.txt`（26ファイル、事前にダウンロードして配置。取得元は [docs/datasets.md](./datasets.md)）
- 各行を `見出し語<TAB>訳語` としてパースする。
- 見出し語カラムはカンマ区切りで複数表記を含みうるため `,` で分割し、それぞれ独立した見出し語として扱う。
- 各見出し語を `.strip().lower()` し、内部の連続空白は単一スペースに正規化する（例: `"Give  Up"` → `"give up"`）。
- 同一正規化見出し語に複数行がヒットした場合は、訳語を `" / "` で連結する（完全重複は除去）。
- `=X` 形式（別見出し語への同義語参照）は、MVPでは参照先をそのまま文字列として保持する（実装コストを抑えるため、参照解決は行わない。将来的な改善候補）。
- 結果: `word -> translation` のマッピング。約47,000エントリ。

### 2. Tatoebaの読み込み・トークナイズ

- 入力: `backend/data/raw/tatoeba/eng_sentences.tsv`（約203万行、取得元は [docs/datasets.md](./datasets.md)）
- 各文をトークナイズする: `re.findall(r"[A-Za-z']+", text.lower())`
- 文中に現れるユニークなトークンごとに、その文の `(sentence_id, text, word_count)` を候補として収集する（同じ文中で同じ単語が複数回出現しても候補は1件のみ）。
- この中間インデックスはビルドスクリプトのプロセス内メモリ上にのみ存在し、DBには書き出さない（サイズが大きいため）。

### 3. 例文選定アルゴリズム

各単語（EJDictの見出し語およびTatoeba語彙に登場する全トークン）について、候補文から1文を選ぶ:

1. 候補 = その単語がトークンとして（部分文字列ではなく単語境界で）出現する文。トークナイズ自体が単語単位で行われているため、この条件は自然に満たされる（例: `cat` は `category` にはマッチしない）。
2. **語形完全一致のみ**（ステミング・見出し語化はしない）。`running` を含む文は `run` を検索した場合の候補にはならない。
3. 文の長さ（単語数）でフィルタ: **4語以上25語以下**の候補に絞る（学習用途として断片的すぎる文・長すぎる文を避けるため）。両閾値はビルドスクリプト内の定数として調整可能。
4. フィルタ後の候補の中から**最短文**を採用する。同じ長さの候補が複数ある場合は **`sentence_id` が最小のもの**を採用する（決定的な結果を保証し、同一データでの再ビルド時に出力が変わらないようにするため）。
5. フィルタ後に候補がゼロの場合は、フィルタをかける前の**全候補中の最短文**にフォールバックする。
6. 候補が完全にゼロ件の場合のみ、その単語の例文は空欄とする。

複数語のEJDict見出し語（フレーズ、例: `give up`）についても同様の考え方を適用する。フレーズの先頭単語の候補文リストを使って検索範囲を絞り込んだ上で、フレーズ全体が単語境界で一致するかを確認する（オフラインのビルド時処理のため、この絞り込みを行っても計算コストは許容範囲）。

### 4. SQLiteへの永続化

出力先: `backend/data/build/ejcsv.db`

```sql
CREATE TABLE dictionary (
  word TEXT PRIMARY KEY,        -- 正規化済み（小文字・trim・空白正規化）
  translation TEXT NOT NULL     -- 日本語訳。語義は " / " で連結
);

CREATE TABLE sentences (
  id INTEGER PRIMARY KEY,       -- Tatoebaのsentence id
  text TEXT NOT NULL
);

CREATE TABLE word_examples (
  word TEXT PRIMARY KEY,        -- 正規化済み。EJDict見出し語に限らずTatoeba語彙全体が対象
  sentence_id INTEGER NOT NULL REFERENCES sentences(id)
);

CREATE TABLE build_meta (
  key TEXT PRIMARY KEY,
  value TEXT                    -- データセットのバージョン、ビルド日時、件数などを記録
);
```

- `word_examples` はEJDictの見出し語だけでなく、Tatoebaの全語彙トークンを対象に構築する。これにより「辞書には載っていないが例文コーパスには存在する単語」でも例文だけはヒットし得る（訳語セルのみ空欄、例文セルは埋まる、というケースを許容する）。
- `sentences` テーブルは、実際に「いずれかの単語の最良例文」として選ばれた文のみを格納する（コーパス全203万文は格納しない）。これによりDBサイズを抑える。

### 5. 生データ・成果物の管理方針

- `backend/data/raw/` は `.gitignore` 対象とする（EJDict・Tatoebaの生データは再ダウンロード可能であり、Tatoebaだけで100MB超あるためリポジトリに含めない）。
- `backend/data/build/ejcsv.db` は **Git LFS でコミットする**方針を推奨する。
  - 理由: Renderへのデプロイ時に外部データソース（GitHub raw URLやTatoebaサーバー）への依存をなくし、デプロイの再現性・信頼性を高めるため。DBサイズは辞書側が約47,000語程度に収まることもあり、数十MB程度で収まる見込み。
  - 代替案: Dockerのビルドステップ内で毎回 `scripts/build_data.py` を実行し、都度生成する方法もある。この場合ビルド時間が伸び、外部ダウンロードの成功が前提になる。データやマッチングロジックの変更頻度が低い本プロジェクトの性質上、LFSでのコミットを第一候補としつつ、この代替案も選択肢として残す。

## 実行方法（実装時に整備）

```bash
cd backend
python scripts/build_data.py \
  --ejdict-dir data/raw/ejdict/src \
  --tatoeba-file data/raw/tatoeba/eng_sentences.tsv \
  --out data/build/ejcsv.db
```

具体的なCLI引数・進捗ログ・エラーハンドリングは実装時に確定する。
